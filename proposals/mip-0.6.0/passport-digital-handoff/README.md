# MIP 0.6.0 passport digital handoff proposal

This directory is a **proposal**, not an active MIP 0.5.0 contract. Its `schemas/`, `enums/`, compliance profile, documentation, and conformance fixtures are isolated copies for review. No service may advertise `passport_digital_handoff`, `DIGITAL_HANDOFF`, or `ICAO_PASSPORT_DIGITAL_HANDOFF` as a MIP 0.5.0 capability. The active files at the repository root must remain byte-for-byte unchanged while this proposal is reviewed.

## Proposal merge, beta candidate, and public release gates

This proposal may merge as documentation and test data while the current public release remains 0.5.0. Its files do not change the active root schemas, enums, supported version, or 0.5.0 discovery. No service may silently accept the new FlowType under `mip_version: 0.5.0`.

Before aggregate beta acceptance, create an **explicit beta-only, versioned 0.6.0 candidate** such as `0.6.0-beta.1` from a reviewed protocol commit. Its immutable candidate manifest MUST name that exact version, protocol commit SHA, SHA-256 of each promoted schema/enum/spec/profile/conformance file and generated binding artifact, and the supported digital-handoff capability. Promote the frozen proposal files, including the Credential Template system-profile ID fix, into candidate inputs; regenerate every affected binding from those exact inputs and prove no drift. Land independently reviewed, executable Marty-owned handoff behavior across UI, Credentials, Core, and supported consumers. Preserve the physical nine-step behavior and TD1/TD2/TD3 routes. The candidate may be merged and deployed **only to beta** for exact-source integration tests and aggregate acceptance; it is not the public 0.6.0 release or a claim of production support.

The proposal's schema IDs use the `0.6.0-beta.1` namespace. Its `schemas/` and `enums/` contain the complete reference closure, including unchanged 0.5.0 definitions copied as candidate inputs. Candidate consumers MUST resolve these IDs from the local, manifest-hash-verified candidate bundle and MUST NOT fetch mutable `main` URLs or overlay candidate definitions onto active 0.5.0 IDs. The candidate manifest pins every copied dependency as well as every changed file. A later candidate version requires its own IDs, hashes, and conformance run.

Beta components MUST advertise the exact candidate version in `X-MIP-Version` and expose `passport_digital_handoff` only through an explicit candidate capability in discovery. A caller MUST request that exact candidate version and capability; each required component MUST prove the same candidate manifest and capability at readiness, otherwise the digital Flow is unavailable and the beta deployment fails readiness. Do not infer support from a highest-common-version negotiation, a 0.5.0 response, or a partially upgraded stack. Production and 0.5.0 participants continue to advertise only 0.5.0 and reject the candidate FlowType. Keep the candidate artifacts and deployment isolated from the public 0.5.0 release.

Only after proposal and candidate conformance, exact-source service/Flow integration tests, independent security/privacy review, and the aggregate beta acceptance soak pass may the team make the separate **public 0.6.0 release**. Then coordinate the root specification, package version, version policy, discovery, release manifest, compatibility tests, bindings, and changelog from the accepted candidate contract; review any delta and rerun affected gates. Tag and publish `0.6.0` only from that coordinated release commit. The beta candidate and its evidence precede this release gate, so acceptance does not depend on an already published public 0.6.0.

Run the proposal checks with `py -3.12 -m pytest -q proposals/mip-0.6.0/passport-digital-handoff/tests`. The proposal validator keeps candidate and active 0.5.0 schema IDs distinct, checks that candidate references close within the candidate bundle, and validates candidate fixtures with a candidate-only registry. Active 0.5.0 schemas are loaded separately only for fixtures unchanged by the proposal. This does not modify or validate the active release as 0.6.0.
